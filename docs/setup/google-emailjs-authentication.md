# إعداد المصادقة والبريد الإلكتروني — نظام راسخ

هذا الدليل يهيّئ الخدمات الخارجية التي لا يمكن تفعيلها بمجرد رفع الكود. لا تضع كلمات مرور أو مفاتيح خاصة في GitHub أو ملفات الواجهة.

## 1. ما أصبح موجودًا في الكود

- تسجيل الدخول بالبريد الإلكتروني وكلمة المرور.
- إنشاء حساب يدوي مع رسالة تأكيد بريد تُستخدم مرة واحدة.
- استعادة كلمة المرور من رابط بريد مؤقت وأحادي الاستخدام.
- زر Google الرسمي عبر Google Identity Services، مع تحقق توقيع ID token وissuer وaudience وexpiry وnonce في الخادم.
- ربط Google بالحساب السابق عند تطابق البريد الموثوق، دون إنشاء شخص أو حساب مكرر.
- الدعوات تُرسل إشعارات بريدية فقط بلا رابط قبول. تُسند الدعوة إلى الحساب الموجود بالبريد نفسه، أو تُفعّل تلقائيًا بعد إنشاء حساب جديد بالبريد نفسه وتأكيد ملكيته.
- إنشاء حساب جديد بالبريد الذي أُرسل إليه إشعار الإضافة؛ وبعد تأكيد ملكية البريد تُطبَّق الدعوات المطابقة تلقائيًا، مع أخذ الدور والنطاق والصلاحيات من سجل الدعوة لا من بيانات المتصفح.
- خيارات التهيئة: جمعية قيد التحقق، مسجد مستقل، مقر قرآني مستقل، وبيئة تجريبية معزولة.

وجود الكود لا يعني أن الخدمات أصبحت متصلة. يجب تنفيذ الخطوات التالية أولًا.

أنشئ قالبين منفصلين في لوحة EmailJS وفق المتغيرات التالية. فصل القوالب يمنع الخلط بين إشعار إضافة عضو ورسالة تأكيد بريد أو استعادة كلمة مرور.

### القالب الأول: إشعار إضافة إلى راسخ

أنشئ Email Template جديدًا وسمّه مثلًا `Rasikh Invitation`. هذه الرسالة إشعار فقط؛ لا تحتوي رابط قبول أو رمز دعوة.

إعداد المستلم والموضوع:

- To Email: `{{to_email}}`
- To Name: `{{to_name}}`
- Subject: `{{subject}}`

جسم الرسالة:

```text
السلام عليكم ورحمة الله وبركاته، {{to_name}}

تمت إضافتك إلى {{organization_name}} في نظام راسخ.

الدور المعيّن لك: {{role_name}}
نطاق العمل: {{scope_name}}
الداعي: {{inviter_name}}
تنتهي صلاحية الإسناد: {{expires_at}}

{{message}}

إذا كان لديك حساب في راسخ، سجّل الدخول بالبريد الإلكتروني نفسه.
وإذا لم يكن لديك حساب، أنشئ حسابًا بالبريد نفسه ثم أكّد ملكية بريدك من رسالة إنشاء الحساب؛ سيُفعّل النظام عضويتك تلقائيًا ويعرض لك المسجد والحلقة المعيّنين لك.

هذه الرسالة إشعار بالإضافة فقط، ولا تحتاج إلى قبول الدعوة من رابط منفصل.
إذا لم تكن تتوقع هذه الإضافة، فتواصل مع الجهة الداعية.
```

بعد حفظ القالب، انسخ Template ID إلى:
`EMAILJS_INVITATION_TEMPLATE_ID`

### القالب الثاني: تأكيد الحساب واستعادة كلمة المرور

أنشئ قالبًا ثانيًا وسمّه مثلًا `Rasikh Account Email`.

إعداد المستلم والموضوع:

- To Email: `{{to_email}}`
- To Name: `{{to_name}}`
- Subject: `{{subject}}`

جسم الرسالة:

```text

{{email_title}}

{{message}}

رابط الإجراء:
{{action_url}}

{{action_label}}

إذا لم تطلب هذا الإجراء، فتجاهل الرسالة ولا تشارك الرابط مع أي شخص.
```

بعد حفظ القالب، انسخ Template ID إلى:
`EMAILJS_ACCOUNT_TEMPLATE_ID`

> ملاحظة: أسماء المتغيرات في القالب يجب أن تطابق الأسماء أعلاه تمامًا. إعداد To Email ضروري حتى يصل البريد إلى المستلم الفعلي.

### مفاتيح EmailJS في استضافة Backend

أضف في إعدادات Secrets أو Environment Variables في استضافة الخادم:

- `EMAILJS_INVITATION_TEMPLATE_ID`
- `EMAILJS_ACCOUNT_TEMPLATE_ID`
- `EMAILJS_PRIVATE_KEY` (اختياري، ويُحفظ سرًا في استضافة الخادم فقط)

مفتاح EmailJS العام ومعرّف الخدمة مضبوطَان افتراضيًا في Backend، ويمكن تجاوزهما بمتغيرات البيئة عند الحاجة. أما Template IDs فلا يمكن تخمينها؛ تُنسخ من القالبين بعد إنشائهما.

الكود ينظم الإرسال على مستوى نسخة الخادم احترامًا لحد EmailJS البالغ رسالة واحدة في الثانية. عند تشغيل أكثر من نسخة Backend يجب استخدام طابور إرسال مشترك على مستوى الخدمة بدل الاعتماد على طابور الذاكرة المحلي.

## 3. إعداد Google Sign-In الحقيقي

1. افتح Google Cloud Console وأنشئ مشروعًا أو اختر مشروعًا مخصصًا لراسخ.
2. أكمل إعداد OAuth consent screen وبيانات التطبيق المطلوبة.
3. أنشئ OAuth Client ID من نوع Web application.
4. في Authorized JavaScript origins أضف أصل موقع الواجهة فقط، مثل:
   `https://YOUR-ACCOUNT.github.io`
   استخدم قيمة `location.origin` الفعلية من صفحة راسخ، ولا تضف مسار المستودع إلى خانة Origin.
5. انسخ Web Client ID (ينتهي غالبًا بـ `.apps.googleusercontent.com`).
6. ضع القيمة نفسها في:
   - `GOOGLE_CLIENT_ID` داخل أسرار Backend.
   - `GOOGLE_CLIENT_ID` في `assets/js/rasikh-config.js`.

لا تضع Google Client Secret في الواجهة. الكود يستخدم Google Identity Services ليعرض زر Google الرسمي؛ ثم يرسل ID token إلى Backend ليُتحقق من توقيعه و`aud` و`iss` و`exp` و`nonce`. ويُستخدم `sub` كمعرّف Google الثابت، وليس البريد وحده.

حسابات Gmail وGoogle Workspace الموثوقة يمكنها تسجيل الدخول مباشرة. أما عنوان بريد خارجي مستخدم في حساب Google فلا يُعامل وحده على أنه إثبات كافٍ لملكية ذلك البريد؛ يلزم تأكيده عبر تسجيل البريد اليدوي.

## 4. إعداد Backend والكوكيز

أضف القيم التالية في استضافة الخادم، ولا ترفع ملف `.env`:

- `DATABASE_URL`: اتصال PostgreSQL الفعلي.
- `COOKIE_SECRET`: قيمة عشوائية قوية لا تقل عن 32 حرفًا.
- `COOKIE_SECURE=true` في الإنتاج.
- `COOKIE_SAME_SITE=none` عندما تكون واجهة GitHub Pages والـBackend على موقعين مختلفين، مع ضرورة `COOKIE_SECURE=true`.
- `CORS_ORIGIN`: أصل الواجهة فقط، دون مسار المستودع، مثل `https://YOUR-ACCOUNT.github.io`.
- `PUBLIC_APP_URL`: الرابط الكامل للصفحة المنشورة مع مسار المستودع، مثل `https://YOUR-ACCOUNT.github.io/YOUR-REPOSITORY`.
- إعدادات EmailJS المذكورة أعلاه.
- `GOOGLE_CLIENT_ID`.

تعتمد الجلسة على Cookie من نوع HttpOnly. إعداد CORS والكوكيز يجب أن يطابق عنوان الواجهة والخادم الفعليين. قد تمنع بعض المتصفحات ملفات تعريف الارتباط التابعة لطرف ثالث؛ الأفضل مستقبلاً وضع الواجهة والـAPI تحت نطاق مملوك واحد أو توفير Proxy من نفس النطاق.

## 5. إعداد الواجهة

في `assets/js/rasikh-config.js`:

- ضع رابط Backend المنشور في `API_BASE_URL` دون `/api/v1` في نهايته.
- ضع Google Web Client ID في `GOOGLE_CLIENT_ID`.

لا تضع في هذا الملف `DATABASE_URL` أو `COOKIE_SECRET` أو `EMAILJS_PRIVATE_KEY` أو أي كلمة مرور.

## 7. اختبار القبول قبل الاستخدام

- إنشاء حساب يدوي وإثبات وصول رابط تأكيد البريد.
- منع الدخول بكلمة المرور قبل تأكيد البريد.
- الدخول بكلمة المرور بعد التأكيد.
- طلب استعادة كلمة المرور والتأكد من انتهاء صلاحية الرابط وعدم إعادة استخدامه.
- ظهور زر Google الرسمي بعد إضافة Client ID، ثم التحقق من إنشاء حساب أو ربط الحساب السابق.
- دعوة بريد جديد: يصل البريد، ويُنشأ حساب من الرابط بالدور المحدد.
- دعوة بريد موجود: يسجل الشخص بالحساب نفسه ويقبل الدعوة؛ لا يتكرر ملف الشخص.
- تجربة بريد مختلف عن بريد الدعوة: يجب أن يُرفض القبول.
- تجربة مساعد حلقة: يستطيع العمل في السجل اليومي ضمن نطاقه، ولا يملك إعدادات التقييم والأوزان.
- تجربة حساب لا يملك صلاحية: لا تظهر له عناصر التنقل غير المصرح بها، ويرفض Backend الطلب حتى لو حاول استدعاء API مباشرة.
- تجربة جمعية غير معتمدة: تبقى قيد التحقق ولا تحصل على صلاحيات تشغيل الجمعية قبل الاعتماد.

حتى إكمال إعداد الاستضافة والقوالب وربط PostgreSQL، تظل بعض الوظائف جاهزة في الكود لكنها غير فعالة على موقع GitHub Pages.
